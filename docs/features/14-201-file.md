# 14. V2 phase 2.1: the 201 file

The employee's 201 file is a checklist of 21 documents: uploads, HR verification, expiry alerts and "I'll submit it by…" dates. It covers roadmap items 9 (GKE → RAE), 16, 17 and 18.

## What you see

- **My Profile** (employee): the checklist with a progress bar. For each document the employee can **Upload** (or **Replace**) a PDF, JPG or PNG. For a missing one they can **Set date** to promise when it will be submitted.
- **Employee record** (HR): the same checklist, plus **Review** on every row:
  - *Mark on file*: verifies an upload, records a paper copy HR already holds, or corrects the expiry date.
  - *Return*: needs a reason. The file is deleted and the employee gets a bell notification and an email saying why.
- **Employees list**: a **201** column, e.g. `7/21`. Documents that are on file but expired don't count.
- **Alerts** (daily, 07:05): 60, 30 and 7 days before a document expires, and on the day. A separate alert goes out when a promised date passes. They reach the employee, HR and Admin.

## Design

| Decision | Why |
| --- | --- |
| `Requirement` enum ported from the old `TwoOOneDocument`, with `GkeReport` → `RaeReport` | The label is one line. The stored **value** is `rae_report`; renaming a value later needs a data migration, renaming a label never does |
| Rows keyed to `employee_profiles`, not `users` | HR starts the 201 file before the employee registers |
| No row = missing | A new hire doesn't need 21 placeholder rows; the checklist query fills the gaps |
| "Expired" is computed, never stored | It can't drift out of date, and no nightly job has to flip a status |
| Office staff skip guard-only documents | `Requirement::isGuardOnly()`: security license, neuro-psych, training, RAE, firing, SOSIA |
| One Livewire component for both audiences | `EmployeeProfilePolicy` decides which buttons appear, and every action re-checks it |
| Employees can upload but never verify | Their upload is `submitted`, and only `manage-people` can mark it `on_file` |

## Files stay consistent with rows

`SubmitRequirementDocument`:

1. Writes the new file to the private disk first.
2. Runs the transaction: locks the row, updates it, writes the audit entry, notifies HR.
3. If the transaction throws, it **deletes the new file** and rethrows.
4. Only after the commit does it delete the **replaced** file.

So a failed save never leaves an orphan, and a successful one never points at a deleted file.

The bytes are checked twice. The component's `mimes:` rule reads the content (not the browser's claim), and `RequirementDocumentStore` checks the file signature (`%PDF-`, PNG, JPEG) again, because an Action can be called from places that skip validation. The original filename is only ever shown back to people. The stored name is random: `201/{profile}/{requirement}-{uuid}.pdf`.

## Private, and every view audited

`/requirements/{id}/document` streams the file after `EmployeeRequirementPolicy::viewDocument`, which allows the employee and HR only. Headers are `no-store` and `nosniff`. Each view writes a `requirement.document_viewed` audit entry, because NBI clearances and medical results are the most sensitive files in the system.

## Alerts

`SendRequirementAlerts` reuses the `sent_alerts` claim from phase 2.0.

- **Nearest threshold only.** With 25 days left, the 30-day alert goes out, not the 60-day one as well. A scheduler that was down for a week never sends two alerts at once.
- **The key includes the expiry date** (`requirement.expiry.30.20261102`). A renewed document with a new date gets a fresh set of alerts.
- Email for the 30-, 7- and 0-day alerts; the 60-day alert goes to the bell only.
- People who have resigned or been terminated are skipped.

## A Livewire trap this phase hit

The upload action was first called `upload()`. In the browser, `wire:submit="upload"` called **Livewire's own JavaScript `$wire.upload()`** and threw. The Pest tests passed anyway, because `->call('upload')` goes straight to PHP and skips the browser.

Two fixes came out of it:
- The method is now `submitDocument()`.
- An architecture test fails if any component defines a public method named like a built-in `$wire` method (`upload`, `refresh`, `watch`, `entangle`, …). It also caught a V1 `PunchLog::refresh()`, now renamed `reloadPunches()`.

Lesson: component tests prove the PHP, while a browser run proves the wiring. Do both.

## Try it

```bash
php artisan migrate:fresh --seed
php artisan app:send-requirement-alerts        # Maria: NBI expires in 20 days, drug test promise overdue
MAIL_MAILER=log php artisan queue:work --stop-when-empty
```

- As `employee@example.test`: My Profile → 201 file. Upload a Police Clearance and set "Valid until".
- As `hr@example.test`: Employees (see the 201 column) → Maria Santos → Review the Birth Certificate. Return it with a reason, then sign back in as Maria to see the reason and the notification.

## Configuration

`config/hr.php` → `documents`: disk (`HR_DOCUMENTS_DISK`, empty = the photo disk), max size (10 MB), allowed types, and alert thresholds (`[60, 30, 7, 0]`; an empty list turns expiry alerts off). On Laravel Cloud the disk **must** be the bucket.
